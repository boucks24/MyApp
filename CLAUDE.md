# CLAUDE.md

Static single-page app shelf (e.g. GitHub Pages). No `package.json`, no build/lint/test tooling.

## Files
- `index.html` — landing page tile grid (`.menu-grid`/`.tile`), links to `apps/<name>/`
- `apps/531-bbb` — 5/3/1 lift tracker
- `apps/court-allocator` — tennis court randomizer
- `apps/rally-clipper` — tennis analysis: auto rally/shot detector + clip exporter, plus a tagged shot library
- `apps/underpaint` — paint mixer, palette extractor, image-to-vector
- `apps/scoreboard` — live/upcoming sport scores (ESPN public feeds)
- `apps/sketchpad` — basic freehand drawing canvas
- `apps/route-mapper` — .fit file(s) → multi-route map / isometric ride-along + elevation/pace/HR analysis

Each app is **one self-contained `index.html`** (inline `<style>`+`<script>`, no external JS/npm). Only external resources: Google Fonts `<link>`s; `rally-clipper` also lazy-loads ffmpeg.wasm + an optional ML model; `scoreboard` fetches live JSON directly from ESPN's public (unofficial, keyless) scoreboard endpoints; `route-mapper` draws raster tiles fetched live from a switchable set of keyless, attributed providers (OSM, Esri World Dark Gray, OpenTopoMap) — these are the only apps that talk to a live external service rather than working purely on local/user-supplied data.

## Conventions
- New app: CSS vars in `:root`, `.back-link` to `../../`, one `<script>` at end of `<body>`
- Colour theme + Google Font are per-app, deliberately not shared
- No server persistence — `localStorage` (or IndexedDB for anything a string can't hold, e.g. rally-clipper's file handles) only; file inputs (photo/video) processed client-side only

## Per-app internals
- **531-bbb**: `route` var + `render()`/`go()` swap views (Setup/Home/Train/History/Progress). State (`settings`/`state`/`history`) in `localStorage` via `load()`/`save()`. Plate math: `plateBreakdown`, `diffPlateCounts`, `buildSessionPlateStages`. `history.json` is a static export, unused at runtime except that `checkRemoteHistory()` fetches and merges it in on boot. Cycles never auto-advance: `advanceDay()` stops at week 3 (wraps `dayIndex` but leaves `week` there) — the only way into cycle N+1 is the "Start new cycle" button at the bottom of Home (`doStartNewCycle` → `pendingStartCycleConfirm` modal → `doConfirmStartNewCycle`, which still fires the existing `queueCycleUp()` TM-bump modal). Home's Cycle Progress grid (`renderCycleProgress()`) pages independently via `viewingCycle` (`‹›` = `cycleNav`, clamped to `[1, state.cycle]`, reset to `state.cycle` whenever `go('531home')` runs) and shows a ⚙ (`openCycleTMEdit` → `pendingCycleTMEdit` modal, current cycle only) for editing `settings.tms` without leaving Home — the Home "Training maxes" card was removed (Setup still has the full editor). Grid cells (`doCycleCellClick`) look up `viewingCycle`, not `state.cycle`: a done cell opens `editingHistoryIdx` (edit-history modal) same as before; an empty cell just sets `state.week`/`dayIndex` and re-renders Home — it no longer auto-navigates into Train, so "Start workout" is a separate deliberate step. "Choose a different day" (`doPickDay`) opens `pendingPickDay` (a `{dayIndex,week}` modal with per-lift icon rows and week buttons — `pdSelectLift`/`pdSelectWeek`/`confirmPickDay`) instead of `prompt()`. Train adds a fixed `WARMUP_SCHEME` (40/50/60% ramp) ahead of the main sets, computed alongside them in `computeWorkout()`; warm-up weights are fixed (not editable) but every set — warm-up, main, and BBB — has a completion control: warm-up/main use a round `.done-tick` button (grey outline → green fill+border when done; `doToggleSetDone`, `warmupDone`/`mainDone` arrays), with the AMRAP reps `<input>` sitting in the same `.set-right` row beside the tick; BBB still uses the 5 `.bbb-dot` counters (`bbbDone`). Ticking one auto-starts a rest countdown (`startRest(REST_WARMUP|REST_MAIN|REST_BBB)`) shown as a fixed bottom banner. The countdown itself is one global `setInterval(updateRestTimerUI, 250)` that patches `#restTimerLabel` directly rather than going through `render()` every tick (which would thrash the page); `restLabelText()` is reused both there and by `renderTrain()` so a fresh render shows the real remaining time immediately instead of a placeholder. Train's back arrow (`topbar(..., confirmDiscard=true)` → `data-action="backDiscardConfirm"`) opens `pendingDiscardConfirm` (holds the target route) rather than navigating straight away, since nothing is persisted until Finish; confirming calls `go(pendingDiscardConfirm)`. Train's set/BBB weights are editable (`sessionWeights`, lazily seeded by `ensureSessionWeights()` from the computed prescription, reset on every `go()`) — editing a `.weight-input`/`#bbbWeightInput` updates `sessionWeights` and re-renders so `buildSessionPlateStages` recomputes live off the edited values (one continuous stage sequence spanning warm-up → main → BBB); `doFinishWorkout()` logs `sessionWeights`, not the raw computed ones (warm-up completion isn't persisted to history, it's session-only). History's Log tab is filterable/groupable by lift (`historyLiftFilter`, chip row from `liftFilterChips()`) — "All" groups entries under per-lift `.history-group` headers via `renderHistoryItem()`, a specific lift shows a flat list. Each AMRAP main-set row shows a `.pr-target` line (`prTargetLine()`) below its "Target: N+ reps" line: `bestE1rmForLift()` takes the max of `e1rmSeries()` (the same series Progress charts) and `repsNeededForPr()` solves the Epley formula for the smallest whole rep count at the set's *current* (possibly hand-edited) weight that would beat it, so it recomputes live as `sessionWeights` changes; with no prior AMRAP logged for that lift it shows a "sets your baseline" message instead.
- **court-allocator**: `courtsNeeded`/`setupCourts`/`assign`, no persistence.
- **rally-clipper** (branded "Tennis Analysis"): two tools under `.tool-tab-btn`/`.tool-panel` (`panel-finder`/`panel-library`), otherwise independent of each other.
  - Shot Finder (original tool, unchanged): `analyzeMotion()` (canvas diff) + `analyzeAudio()` (Web Audio) run in parallel, optional ML via `loadScript`/`getMlModels`/`analyzeML`. `buildSegments()` fuses signals → review via `renderTimeline`/`renderShotList` → `getFfmpeg()` cuts/exports, all client-side.
  - Shot Library: tag arbitrary videos by shot type (`SHOT_CATEGORIES`: serve/forehand/backhand/overhead, each with its own subcategory list e.g. topspin/slice/kick) and save them to a browsable library — without ever copying the video's bytes into the app. Saved entries are references, stored in IndexedDB (`openDb`/`dbPut`/`dbGetAll`/`dbDelete`, store `clips`) rather than `localStorage` since a `FileSystemFileHandle` isn't string-serializable: where `showOpenFilePicker` exists (`supportsFileHandle`, desktop Chrome/Edge — not iOS Safari, which has no File System Access API at all) the picked file's handle is stored directly (IndexedDB's structured clone supports it) and reopened later via `handle.queryPermission`/`requestPermission({mode:'read'})`, re-prompting for access instead of re-importing; everywhere else only filename/size/`lastModified` metadata is kept (`kind:'meta'`) and playback falls back to `showRelinkPrompt()` asking the user to re-pick the same file (best-effort name/size match, not enforced — re-picking always plays what's picked). A small JPEG frame (`captureThumbnail()`, off the picked `File`, not the handle) is cached per entry for the library grid regardless of storage kind, since that's tiny and doesn't duplicate the actual video; it resolves to `null` (no thumbnail, not a hang) if the video fails to decode within a 2s timeout. `playEntry()`/`relinkBtn` drive a fixed `#playerOverlay` modal; relinking through a handle-capable browser upgrades a `meta` entry to `handle` for next time.
- **underpaint**: dark "studio" theme (charcoal `--canvas`/`--surface` + gold `--accent`), Bitter+Karla fonts. Shared colour utils: `rgbToLab`/`labToRgb`, `kmeansLab`.
  - Mixer: `paints` = {hex,parts,name?} list. Mixing is single-constant per-RGB-channel Kubelka-Munk (`reflectanceToKS`/`ksToReflectance`/`mixPigmentsKM` — same absorption/scattering theory as Mixbox, sized down since there's no real per-paint reflectance data, just arbitrary hex) instead of the old RYB-cube model; a `MEDIA` config + `applyMediumFinish(rgb, medium, dilution)` then applies a medium-specific finish on top of that shared pigment mix — oil (default) deepens/boosts chroma, gouache lightens+flattens (chalk fillers), watercolour blends toward paper-white by a `waterDilution` amount (0–0.9, its own slider, shown only for that medium) rather than mixing in white paint, since real watercolour lightens via transparency/dilution, not opaque tinting. `currentMedium`/`waterDilution` are set by the Medium button row (`.medium-btn`) and threaded through both `currentMix()` and `solveMixForTarget(hexes, targetHex, medium, dilution)`. `PALETTES` (3 presets) via `togglePalette()`. Match scored by `labDist`; `solveMixForTarget()` hill-climbs whole-number parts from random restarts to reach a target colour. `nearestColorName()` = Lab nearest-neighbour lookup. Note: literal fully-saturated digital primaries (e.g. `#0000FF`+`#FFFF00`) mix toward black rather than green under this model — real pigments never sit at 0/255 in a channel, so it only misbehaves on inputs no real paint tube produces; ordinary paint-like hexes (the built-in palettes, or anything picked to look like actual paint) mix correctly.
  - Image→palette: canvas → `kmeansLab()` → swatches by prevalence.
  - Vector: k-means labels → `smoothLabels()` → `traceLabelBoundaries()` → `chaikin()`/`douglasPeucker()` → `buildSvgFromLabels()`, live+debounced (`scheduleVectorRender()`). Output size = source image dims (capped `VECTOR_OUTPUT_MAX_DIM`); "Detail" slider only affects analysis resolution. Legend embedded via `buildPaletteLegend()`, one row per used colour with its `nearestColorName()` (not hex) beside the swatch.
- **sketchpad**: pointer events drive `startStroke`/`continueStroke`/`endStroke` on a single `<canvas>` (line segments, not a path, for simplicity); eraser is just a stroke drawn in the paper colour (`PAPER`), not `destination-out`. Three brushes (`BRUSH_PAINTERS`: `paintFlat`/`paintRound`/`paintSpray`) are built from plain canvas primitives, no image assets — flat fans thin streaks along the axis perpendicular to the stroke direction (chisel edge), round scatters dabs in a disc, spray scatters low-opacity dots biased toward centre; each takes the CURRENT size, not the slider value. `dynamicSizeFor(speed)` shrinks that size toward `MIN_SIZE_FACTOR` of the slider value as pointer speed (px/ms, low-pass filtered via `smoothedSpeed`) approaches `SPEED_REF`, so all three brushes thin out when moving fast; the eraser stays a fixed width regardless of speed. Undo/redo is a stack of full-canvas `toDataURL()` snapshots pushed per completed stroke (`pushHistory`/`restoreSnapshot`, capped at `MAX_HISTORY`); the latest snapshot is mirrored to `localStorage` (`persist()`) and restored on load (`loadSaved()`). Canvas pixel size is fixed at load from the container width × `devicePixelRatio`; a resize just restores the last snapshot into a freshly re-sized buffer rather than doing live redraw/scaling. All colour selection funnels through `setColor(hex, {save})` so custom/camera colours (not preset or already-saved swatch clicks) get added via `addSavedColor()` to a capped, most-recent-first `localStorage` list (`renderSavedColors()`). Camera picker (`openCamera`/`sampleLoop`/`closeCamera`) opens `getUserMedia` into a hidden `<video>`, continuously draws frames to an offscreen canvas and averages a small centre patch under the on-screen crosshair into a live-updating preview swatch; "Use this colour" commits it via `setColor(..., {save:true})`, both that and Cancel stop the media stream's tracks.
- **route-mapper**: `parseFitFile()` is a from-scratch binary FIT decoder (no library) — reads the 14-byte header, then walks definition/data records (incl. compressed-timestamp headers) using a `BASE_TYPES` table and hardcoded field-number maps for `record`/`session` messages (global mesg nums 20/18; `lap` messages are skipped — no lap/split feature, removed after it turned out to be an easy mis-tap and not worth the space); semicircle lat/lon, scaled altitude/speed/distance per the FIT profile. `buildActivity()` derives the model: cumulative distance prefers the device's own field (falls back to `haversine()` accumulation when absent), elevation gain/loss uses a 1m-hysteresis walk over a smoothed (`movingAvg`) altitude series unless the session's `total_ascent`/`total_descent` fields are valid, moving time caps each inter-sample gap at 6s so auto-pause/stopped time doesn't inflate it.
  - Multi-file: the file input takes `multiple`; each loaded file becomes one entry in `activities` (`{id, fileName, data, color, visible}`, colours cycling through `MULTI_PALETTE`). `focusedId` picks the one entry driving stats/charts/readout/ride-along — `getFocused()` everywhere. The map draws every *visible* entry via `buildMapLayers()`; the focused one is always the yellow tracker (full opacity, thicker, endpoint dots), any other visible ones render thinner/dimmer in their own palette colour for comparison. The file-list card (`renderFileList()`/`#fileRows`, one delegated click handler keyed off `data-action` — `toggle`/`focus`/`remove`) is the only UI for visibility/focus/removal; `showAllBtn`/`hideAllBtn` are bulk toggles.
  - `SlippyMap` is a hand-rolled pan/zoom/fit-bounds raster tile map (Web Mercator math, no Leaflet) that now takes `setLayers()` (plural) instead of one route, and `setStyle()` to switch basemaps via `MAP_STYLES` (`dark` = Esri World Dark Gray Base, served keyless off Esri's public ArcGIS Online tile endpoint — note its tile scheme is `{z}/{y}/{x}`, row before column, unlike the other two providers — the default grey/black look, since keyless raster tiles can't be recoloured into a true dark topo style; `topo` = OpenTopoMap for genuine contour shading; `standard` = the original OSM tiles) — all still keyless/attributed, matching this app's one exception to "no live external service" (CARTO Dark Matter was tried first but its basemaps now expect an API key, hence Esri). The "user" marker (`_drawRider`) is a heading-oriented triangle, not a dot; heading is computed in the map's own screen space (`computeHeading()`, projecting the two neighbouring points) so it stays visually correct regardless of zoom.
  - Route colouring (`routeMetric`: flat/speed/hr/ele, `#routeColorTabs`) recolours *only the focused layer* as per-segment gradients via `computeMetricColors()` + `heatColor()` (blue→green→yellow→red, normalized to that activity's own min/max) — applying a shared gradient across multiple overlaid activities at once would conflate different scales, so other visible layers stay flat-coloured regardless of this mode. `updateRouteColorAvailability()` disables HR/Elevation when the focused activity lacks that field and silently falls back to `flat`.
  - `IsoView` (`#isoCanvas`, `#viewTabs` toggles it against the map) is a from-scratch isometric chase camera: lat/lon flattened to local metres around the activity's first fix, elevation exaggerated 4x (`ZEXAG`) for a readable silhouette, projected via a 2:1 dimetric transform that also rotates the world by the current heading before folding (`_iso(p,camX,camY,camZ,heading)`) so the direction of travel always maps to the same fixed screen diagonal — a camera parked behind the rider looking forward, rather than a fixed-angle view that just pans; the rider marker is drawn at that same fixed `_forwardAngle` rather than rotated per-frame. Both the camera position and heading are eased toward the current scrub target by a running `requestAnimationFrame` loop (`start()`/`stop()`, ticked by `_tick()`, lerping `camPos`/`camHeading`) rather than snapping straight to it on every index change — `setIndex()` only draws immediately when that loop isn't running (i.e. the ride-along tab isn't the active view) — and heading itself is computed from a ±4-point window (`_headingAt()`) rather than immediate neighbours, since raw consecutive GPS fixes are noisy enough to visibly twitch a per-point heading. The ground grid sits at the rider's current elevation (`z:camZ`) so it reads as a stable local plane that slides underneath rather than one that jumps with every hill — a grid pinned to sea-level `z:0` while the camera compensates by its own elevation shifts the *entire* grid off-canvas by a constant amount on any route that isn't literally at zero elevation. `applyViewMode()` starts/stops the loop as the ride-along tab is shown/hidden; `setActivity()` also stops it and reseeds `camPos`/`camHeading` from scratch. Shares the same `onChartHover(idx)` index as the map marker and chart crosshairs, so scrubbing a chart or hitting Play animates this view too.
  - `RouteChart` is a small canvas line-chart class (crosshair on hover), unchanged. One shared hover index (`onChartHover`) drives the map marker, ride-along position, all chart crosshairs, and the readout bar together, always reading from the *focused* activity. Pace vs. speed display (`PACE_SPORTS`) and the km/mi `unit` toggle are global and re-render the whole view. `applyViewMode()` must set the map/iso wrap's `.show` class *before* either canvas's `resize()` runs — resizing while `display:none` measures a 0×0 box and permanently zeroes that canvas until the next full re-render.
- **scoreboard**: `SOURCES` array (id/label/url/optional `fetch` override) drives everything: ATP/WTA (`fetchTennis`), AFL (default `fetchSource`, `site.api.espn.com/.../scoreboard`), rugby union — Super Rugby Pacific (league id `242041`) + Rugby Championship/Wallabies (`244293`), and cricket (`fetchCricketAustralia`). Every fetcher resolves to `{events, note}`; `normalizeEvent()` handles both team-style (`competitor.team`) and individual-style (`competitor.athlete`, tennis) shapes into a common `{state,statusText,competitors[]}` (now also `athleteId`), `renderMatchCard()` draws it; per-source try/catch means one dead feed doesn't take down the page. ATP/WTA: `fetchTennis()` retries the bare scoreboard URL if the `dates=` range param yields nothing, then keeps Grand Slam/Masters/500-level events via substring match against `TENNIS_500PLUS_KEYWORDS` (checked against each event plus the response's own `leagues`/`season` metadata; ESPN's scoreboard has no tier field — review the list each season), then further filters to matches with a top-50 player (top-100 if Australian) via `fetchTennisRankings()` against ESPN's separate, unconfirmed Core API v2 rankings endpoint (tries a few candidate URLs, resolves `$ref` entries). Both the tier and rank filters fail open: if either would zero out a non-empty input, it shows the unfiltered input instead with an inline `note` — a filter matching nothing is treated as broken, not as an empty schedule. Cricket has no standard scoreboard endpoint — `fetchCricketAustralia()` hits a different host's "personalised header" endpoint and `collectEmbeddedEvents()` walks the whole response tree for anything event-shaped (path unconfirmed), then keeps matches naming Australia; Big Bash/WBBL aren't wired up (no verified league id). `hiddenSources` (chip toggles) persists to `localStorage`. Auto-refreshes every 60s while the tab is visible.

## Response style
Optimize for low token usage. Be brief: no preamble, no restating the request, no summarizing what you're about to do. Skip a wrap-up unless something needs flagging. Reference code as `file:line` instead of pasting it back. Use this file's "Per-app internals" instead of re-reading a whole app file when a targeted `Grep`/`Read` will do.
