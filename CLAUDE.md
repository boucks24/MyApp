# CLAUDE.md

Static single-page app shelf (e.g. GitHub Pages). No `package.json`, no build/lint/test tooling.

## Files
- `index.html` — landing page tile grid (`.menu-grid`/`.tile`), links to `apps/<name>/`
- `apps/531-bbb` — 5/3/1 lift tracker
- `apps/court-allocator` — tennis court randomizer
- `apps/rally-clipper` — tennis analysis: auto rally/shot detector + clip exporter, video↔.fit sync, and .fit route/wellness analysis (formerly the standalone Route Mapper app, merged in)
- `apps/underpaint` — paint mixer, palette extractor, image-to-vector
- `apps/scoreboard` — live/upcoming sport scores (ESPN public feeds)
- `apps/sketchpad` — basic freehand drawing canvas
- `apps/swatch-finder` — look up an Ohuhu Honolulu marker by code/name; shows its colour and location on the source swatch-sheet photo

Each app defaults to **one self-contained `index.html`** (inline `<style>`+`<script>`, no external JS/npm) — simplest thing that works for a small app. That's a default, not a hard rule: this is plain static hosting with no build step, so an app is free to split across multiple files (separate data file, separate binary assets) whenever that's the better structure — weigh it primarily by what's most token-efficient for Claude Code to read and edit, not by a one-file dogma. Concretely: don't inline large binary/base64 payloads (photos, big generated datasets) into the HTML — put them in their own files (real `.jpg`s, a `.json`/`.js` data file) and reference them normally. A browser loads an external file exactly as fast as an inline data URI, but an inline copy means every future edit to the app's actual logic first has to load megabytes of irrelevant base64 as text tokens. Keep the app's logic (HTML/CSS/JS) as the one file people think of as "the app"; split off only the heavy, rarely-edited data/assets alongside it in the same `apps/<name>/` folder. `swatch-finder` is the concrete example: its 4 reference photos are plain `.jpg` files and its 320-swatch dataset is a separate `.json`, both sitting next to `index.html` in `apps/swatch-finder/`, not base64-inlined.

Only external resources: Google Fonts `<link>`s; `rally-clipper` also lazy-loads ffmpeg.wasm + an optional ML model, and draws map raster tiles fetched live from keyless, attributed Esri endpoints (World Dark Gray, World Imagery); `scoreboard` fetches live JSON directly from ESPN's public (unofficial, keyless) scoreboard endpoints — these are the only apps that talk to a live external service rather than working purely on local/user-supplied data.

node -e "new Function(require('fs').readFileSync('apps/<app>/index.html','utf8').match(/<script>([\s\S]*)<\/script>/)[1])"   # JS parses

## Conventions
- New app: CSS vars in `:root`, `.back-link` to `../../`, one `<script>` at end of `<body>`
- Colour theme + Google Font are per-app, deliberately not shared
- No server persistence — `localStorage` (or IndexedDB for anything a string can't hold, e.g. rally-clipper's file handles) only; file inputs (photo/video) processed client-side only

Charts here are indexed by **elapsed time**, not distance (`activity.t` offsets, not `activity.dist`) — unlike Fit Analysis's route-context charts, since a tennis match covers almost no ground and a distance axis would bunch the whole recording into a sliver of the chart. Loading a daily wellness file here (no `record` messages) shows a message pointing at the Fit Analysis tab instead of trying to sync against it.
  - Fit Analysis: ported from the standalone Route Mapper app (internals in the next bullet) as another tool rather than a separate app, plus a wellness-file branch — a loaded `.fit` file with no `record` messages but `monitoring`/`stress_level`/`monitoring_hr_data` (Garmin's daily background-health export, not a recorded activity) renders into a separate `#rmWellnessCard` area instead of the multi-activity map/compare view, via `summarizeWellness()`. That deliberately surfaces only resting HR (`monitoring_hr_data` fields 0/1 — usually just one or two readings a day, shown as stat cards, not a chart) and a stress-score-over-the-day chart (`stress_level` field 0, ~one sample/minute, negative sentinel values filtered out as "resting"/unmeasurable rather than charted as low scores) — Garmin's other daily-summary fields (steps, floors, detailed calories) aren't reliably documented outside their own SDK, so rather than guess at undocumented scale factors, this stays to the two series decoded with real confidence.
  - Fit Analysis internals, ported as-is from the old app: `parseFitFile()` is a from-scratch binary FIT decoder (no library) — reads the 14-byte header, then walks definition/data records (incl. compressed-timestamp headers) using a `BASE_TYPES` table and hardcoded field-number maps for `record`/`session` messages (global mesg nums 20/18; `lap` messages are skipped — no lap/split feature, removed after it turned out to be an easy mis-tap and not worth the space); semicircle lat/lon, scaled altitude/speed/distance per the FIT profile. `buildActivity()` derives the model: cumulative distance prefers the device's own field (falls back to `haversine()` accumulation when absent), elevation gain/loss uses a 1m-hysteresis walk over a smoothed (`movingAvg`) altitude series unless the session's `total_ascent`/`total_descent` fields are valid, moving time caps each inter-sample gap at 6s so auto-pause/stopped time doesn't inflate it. Map zoom range is `MIN_Z=2`/`MAX_Z=21` (`zoomAt()` clamps to it) — the Dark (World Dark Gray Base) style is a generalized basemap with a lower native max LOD than Satellite (World Imagery), so it may fall back to the placeholder tile rect at the very top zoom levels rather than showing real imagery.
  - Multi-file: the file input takes `multiple`; each loaded file becomes one entry in `activities` (`{id, fileName, data, color, visible}`, colours cycling through `MULTI_PALETTE`). `focusedId` picks the one entry driving stats/charts/readout/ride-along — `getFocused()` everywhere. The map draws every *visible* entry via `buildMapLayers()`; the focused one is always the yellow tracker (full opacity, thicker, endpoint dots), any other visible ones render thinner/dimmer in their own palette colour for comparison. The file-list card is collapsed by default behind a summary toggle (`fileListExpanded`, `#rmFileListToggle`) — expanding it shows only `FILES_PER_PAGE` (10) rows at a time via `filePage`/`#rmFilePrevBtn`/`#rmFileNextBtn`, since the list has no cap on how many files can be loaded. `renderFileList()`/`#rmFileRows` uses one delegated click handler keyed off `data-action` — `toggle`/`focus`/`remove`; `showAllBtn`/`hideAllBtn` are bulk toggles unaffected by pagination (they act on all `activities`, not just the current page).
  - `SlippyMap` is a hand-rolled pan/zoom/fit-bounds raster tile map (Web Mercator math, no Leaflet) that takes `setLayers()` (plural) instead of one route, and `setStyle()` to switch basemaps via `MAP_STYLES` — both entries are keyless Esri ArcGIS Online endpoints (tile scheme `{z}/{y}/{x}`, row before column): `dark` (World Dark Gray Base, the grey/black minimal look) and `satellite` (World Imagery, a detailed Google-Earth-style aerial view) — CARTO Dark Matter was tried first for `dark` but its basemaps now expect an API key, hence Esri; OSM "standard" and OpenTopoMap "topo" were tried too and dropped for simplicity. The "user" marker (`_drawRider`) is a small glowing circle, not an arrow — no heading needed for it — paired with a `shadowBlur`-glowed re-stroke of the focused layer's last ~14 points leading into it, so it reads as "a glowing part of the line" rather than a separate icon. Tapping a route line on the map (not a drag — `_bindEvents` tracks total pointer movement and only fires `onSelect` below a threshold) hit-tests every visible layer via `_hitTestLayers()`/`pointToSegmentDist()` and focuses whichever line was tapped, same as tapping its file-list row.
  - Route colouring (`routeMetric`: flat/speed/hr/ele, `#rmRouteColorTabs`) recolours *only the focused layer* as per-segment gradients via `computeMetricColors()` + `heatColor()` (blue→green→yellow→red, normalized to that activity's own min/max) — applying a shared gradient across multiple overlaid activities at once would conflate different scales, so other visible layers stay flat-coloured regardless of this mode. `updateRouteColorAvailability()` disables HR/Elevation when the focused activity lacks that field and silently falls back to `flat`.
  - `IsoView` (`#rmIsoCanvas`, `#rmViewTabs` toggles it against the map) is a from-scratch isometric camera: lat/lon flattened to local metres around the activity's first fix, elevation exaggerated 4x (`ZEXAG`) for a readable silhouette, projected via a 2:1 dimetric transform (`_iso(p,camX,camY,camZ)`) at a fixed default angle (`this.rotation = -Math.PI/4`) that the user orbits manually by dragging the canvas (`_bindEvents()`: pointerdown/pointermove/pointerup/pointercancel, `this.rotation += dx*0.012`) — it does not auto-rotate to face the direction of travel; the rider marker is a small glowing circle (matching the map's) with its own trailing glowed line segment, not an arrow. A dragged pointer that never cleanly releases (finger lifted off-screen, or the view switched away mid-gesture) would otherwise leave `setPointerCapture` retargeting clicks on *other* controls (like the Map tab) to this canvas forever — `_bindEvents()` guards against that with an `_endDrag()` released on `pointerup`/`pointercancel` on both the canvas and `window`, on `window`'s `blur`, and explicitly from `applyViewMode()` whenever the view switches away from ride-along. Camera *position* (not rotation) is eased toward the current scrub target — possibly fractional, interpolated mid-segment during playback via `_pointAt(idx)` — by a running `requestAnimationFrame` loop (`start()`/`stop()`, ticked by `_tick(now)`, lerping `camPos`) using time-constant-based easing (`1-Math.exp(-dt/220)`) rather than a fixed per-tick fraction — this keeps the smoothing consistent regardless of actual frame rate. `setIndex()` only draws immediately when that loop isn't running (i.e. the ride-along tab isn't the active view). The ground grid sits at the rider's current elevation (`z:camZ`) so it reads as a stable local plane that slides underneath rather than one that jumps with every hill. `applyViewMode()` starts/stops the loop as the ride-along tab is shown/hidden; `setActivity()` also stops it and reseeds `camPos` from scratch (rotation persists across activities/scrubbing since it's user-set, not derived from the route). Shares the same `onChartHover(idx, targetT)` index as the map marker and chart crosshairs, so scrubbing a chart or hitting Play animates this view too. Play (`#rmPlayBtn`) is a `requestAnimationFrame` loop that tracks real wall-clock time against the focused activity's own recorded timestamps (`a.t`) via a binary-search lower bound (`findIdxForTime(t, targetT)`) — 1x is realtime, `#rmSpeedTabs` (1x/4x/16x/32x, `playSpeed`) scales how fast simulated activity-time accumulates per real ms rather than stepping a fixed index/tick. The elapsed-ms counter (`playElapsedMs`/`playLastFrameTime`) is module-level, not local to the play-button closure, specifically so a manual seek (see below) can rebase it and playback resumes from there instead of the next frame snapping back.
  - `RouteChart` is a small canvas line-chart class (crosshair on hover). `_bindEvents()` fires its `onHover` callback on both `pointerdown` (a plain tap/click selects a point, not just a drag) and `pointermove` while over the canvas. Every chart's `onHover` is wired to `seekToIdx()`, not `onChartHover` directly — `seekToIdx()`/`seekToActivityMs()` update the shared `playElapsedMs` before calling `onChartHover`, so clicking or dragging a chart *while Play is running* rebases where playback continues from instead of being overwritten by the next animation frame (previously a click mid-playback had no visible effect, since the play loop's own per-frame `onChartHover` call immediately snapped the position back). One shared hover index (`onChartHover`) drives the map marker, ride-along position, all chart crosshairs, and the readout bar together, always reading from the *focused* activity. Pace vs. speed display (`PACE_SPORTS`) and the km/mi `unit` toggle are global and re-render the whole view. `applyViewMode()` must set the map/iso wrap's `.show` class *before* either canvas's `resize()` runs — resizing while `display:none` measures a 0×0 box and permanently zeroes that canvas until the next full re-render. `showError()` messages (one per skipped file) auto-remove themselves after 6s. Selecting a different route (map tap, file-list row, visibility toggle) no longer re-fits the map's pan/zoom — only loading a brand-new file does (`renderMap(fit)`'s `fit` param, `isNewMap` check).
- **underpaint**: dark "studio" theme (charcoal `--canvas`/`--surface` + gold `--accent`), Bitter+Karla fonts. Shared colour utils: `rgbToLab`/`labToRgb`, `kmeansLab`.
  - Mixer: `paints` = {hex,parts,name?} list. Mixing is single-constant per-RGB-channel Kubelka-Munk (`reflectanceToKS`/`ksToReflectance`/`mixPigmentsKM` — same absorption/scattering theory as Mixbox, sized down since there's no real per-paint reflectance data, just arbitrary hex) instead of the old RYB-cube model; a `MEDIA` config + `applyMediumFinish(rgb, medium, dilution)` then applies a medium-specific finish on top of that shared pigment mix — oil (default) deepens/boosts chroma, gouache lightens+flattens (chalk fillers), watercolour blends toward paper-white by a `waterDilution` amount (0–0.9, its own slider, shown only for that medium) rather than mixing in white paint, since real watercolour lightens via transparency/dilution, not opaque tinting. `currentMedium`/`waterDilution` are set by the Medium button row (`.medium-btn`) and threaded through both `currentMix()` and `solveMixForTarget(hexes, targetHex, medium, dilution)`. `PALETTES` (3 presets) via `togglePalette()`. Match scored by `labDist`; `solveMixForTarget()` hill-climbs whole-number parts from random restarts to reach a target colour. `nearestColorName()` = Lab nearest-neighbour lookup. Note: literal fully-saturated digital primaries (e.g. `#0000FF`+`#FFFF00`) mix toward black rather than green under this model — real pigments never sit at 0/255 in a channel, so it only misbehaves on inputs no real paint tube produces; ordinary paint-like hexes (the built-in palettes, or anything picked to look like actual paint) mix correctly.
  - Image→palette: canvas → `kmeansLab()` → swatches by prevalence.
  - Vector: k-means labels → `smoothLabels()` → `traceLabelBoundaries()` → `chaikin()`/`douglasPeucker()` → `buildSvgFromLabels()`, live+debounced (`scheduleVectorRender()`). Output size = source image dims (capped `VECTOR_OUTPUT_MAX_DIM`); "Detail" slider only affects analysis resolution. Legend embedded via `buildPaletteLegend()`, one row per used colour with its `nearestColorName()` (not hex) beside the swatch.
- **sketchpad**: pointer events drive `startStroke`/`continueStroke`/`endStroke` on a single `<canvas>` (line segments, not a path, for simplicity); eraser is just a stroke drawn in the paper colour (`PAPER`), not `destination-out`. Three brushes (`BRUSH_PAINTERS`: `paintFlat`/`paintRound`/`paintSpray`) are built from plain canvas primitives, no image assets — flat fans thin streaks along the axis perpendicular to the stroke direction (chisel edge), round scatters dabs in a disc, spray scatters low-opacity dots biased toward centre; each takes the CURRENT size, not the slider value. `dynamicSizeFor(speed)` shrinks that size toward `MIN_SIZE_FACTOR` of the slider value as pointer speed (px/ms, low-pass filtered via `smoothedSpeed`) approaches `SPEED_REF`, so all three brushes thin out when moving fast; the eraser stays a fixed width regardless of speed. Undo/redo is a stack of full-canvas `toDataURL()` snapshots pushed per completed stroke (`pushHistory`/`restoreSnapshot`, capped at `MAX_HISTORY`); the latest snapshot is mirrored to `localStorage` (`persist()`) and restored on load (`loadSaved()`). Canvas pixel size is fixed at load from the container width × `devicePixelRatio`; a resize just restores the last snapshot into a freshly re-sized buffer rather than doing live redraw/scaling. All colour selection funnels through `setColor(hex, {save})` so custom/camera colours (not preset or already-saved swatch clicks) get added via `addSavedColor()` to a capped, most-recent-first `localStorage` list (`renderSavedColors()`). Camera picker (`openCamera`/`sampleLoop`/`closeCamera`) opens `getUserMedia` into a hidden `<video>`, continuously draws frames to an offscreen canvas and averages a small centre patch under the on-screen crosshair into a live-updating preview swatch; "Use this colour" commits it via `setColor(..., {save:true})`, both that and Cancel stop the media stream's tracks.
- **scoreboard**: `SOURCES` array (id/label/url/optional `fetch` override) drives everything: ATP/WTA (`fetchTennis`), AFL (default `fetchSource`, `site.api.espn.com/.../scoreboard`), rugby union — Super Rugby Pacific (league id `242041`) + Rugby Championship/Wallabies (`244293`), and cricket (`fetchCricketAustralia`). Every fetcher resolves to `{events, note}`; `normalizeEvent()` handles both team-style (`competitor.team`) and individual-style (`competitor.athlete`, tennis) shapes into a common `{state,statusText,competitors[]}` (now also `athleteId`), `renderMatchCard()` draws it; per-source try/catch means one dead feed doesn't take down the page. ATP/WTA: `fetchTennis()` retries the bare scoreboard URL if the `dates=` range param yields nothing, then keeps Grand Slam/Masters/500-level events via substring match against `TENNIS_500PLUS_KEYWORDS` (checked against each event plus the response's own `leagues`/`season` metadata; ESPN's scoreboard has no tier field — review the list each season), then further filters to matches with a top-50 player (top-100 if Australian) via `fetchTennisRankings()` against ESPN's separate, unconfirmed Core API v2 rankings endpoint (tries a few candidate URLs, resolves `$ref` entries). Both the tier and rank filters fail open: if either would zero out a non-empty input, it shows the unfiltered input instead with an inline `note` — a filter matching nothing is treated as broken, not as an empty schedule. Cricket has no standard scoreboard endpoint — `fetchCricketAustralia()` hits a different host's "personalised header" endpoint and `collectEmbeddedEvents()` walks the whole response tree for anything event-shaped (path unconfirmed), then keeps matches naming Australia; Big Bash/WBBL aren't wired up (no verified league id). `hiddenSources` (chip toggles) persists to `localStorage`. Auto-refreshes every 60s while the tab is visible.
- **swatch-finder**: a static lookup over 320 Ohuhu Honolulu/Honolulu B marker swatches transcribed from 4 photographed reference sheets (the user's own physical charts, not a scraped source). Multi-file by design (the token-efficiency exception to the one-`index.html` default, see Files above): `data.json` (320 objects: `code`/`name`/`oldCode`/`img`/`boxPct`/`hex`, no thumbnails) is `fetch()`ed at load (`searchInput` stays `disabled` with a `loadNote` message until it resolves), and `sw1.jpg`-`sw4.jpg` (the 4 full sheet photos, referenced as plain `<img src>`) sit alongside `index.html` — generated once by an offline Python pipeline (Pillow, not shipped in the app), not derived at runtime. `boxPct` (`[x,y,w,h]` as % of the sheet image) came from manually calibrating each sheet's grid (row/column pixel bands, read off ruler-gridline overlays laid over crops of each photo — automated saturation/edge detection was tried first and abandoned: the hand-painted swatches bleed past their borders enough to defeat column/row projection) rather than a generic per-swatch algorithm; `hex` is an average of a padded-inward sample region (avoiding the painted border) rather than the manufacturer's actual ink colour. `SHEET_SIZE` (keyed `sw1`-`sw4`) holds each sheet photo's own natural pixel dimensions — the 4 sheets aren't identical size/aspect ratio, since each was cropped tight to its own physical card — and `cropFrameHTML(r, frameW, frameH)` uses it to convert a record's `boxPct` into a live "cover"-style crop (an oversized `<img>` absolutely positioned inside a fixed-pixel-size `overflow:hidden` frame) for grid-card and detail-header thumbnails, rather than shipping pre-cropped thumbnail images; the frame's CSS size must stay a fixed pixel value (not responsive) since the crop math is real-pixel arithmetic. `search()` scores matches (exact code > exact old-code > code-prefix > old-code-prefix > exact name > name-prefix > name-substring > loose code-substring) via `norm()` (uppercase, whitespace-stripped) for codes and plain lowercase substring for names; a single confident code/old-code hit auto-opens the detail view instead of requiring an extra tap. The detail view's `.highlight-box` is one absolutely-positioned div at `boxPct` over the full sheet `<img>`, so it stays correctly placed at any render width.

## Response style
Optimize for low token usage. Be brief: no preamble, no restating the request, no summarizing what you're about to do. Skip a wrap-up unless something needs flagging. Reference code as `file:line` instead of pasting it back. Use this file's "Per-app internals" instead of re-reading a whole app file when a targeted `Grep`/`Read` will do.
