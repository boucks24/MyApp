# apps/rally-clipper

Branded "Tennis Analysis" in the UI. See root `CLAUDE.md` for repo-wide conventions.

Tennis analysis: auto rally/shot detector + clip exporter, video↔.fit sync, and a pose-similarity photo montage builder. Three tools under `.tool-tab-btn`/`.tool-panel` (`panel-finder`/`panel-sync`/`panel-montage`). FIT parsing/activity-model/formatting/`RouteChart` are shared top-level code (not in any tool's own IIFE, since they're pure/stateless) sitting between Shot Finder's IIFE and the others; each tool is otherwise its own IIFE, independent of the rest. Element IDs and classes left over from the former standalone Route Mapper app are `rm`-prefixed (`.rm-dual-drop`, `.rm-sync-readout`, …) on a `--rm-*` custom-property palette that aliases onto this app's own court/clay/ball theme, specifically to avoid colliding with Shot Finder's pre-existing `dropzone`/`fileInput`/etc. Pose Montage's own ids/classes are `pm`-prefixed for the same reason.

**A fourth tool, Fit Analysis, was removed** — the Route Mapper port that drew a route on a slippy map, an isometric ride-along and a wellness-file view. It was the one part of this app that had nothing to do with tennis. Going with it: `SlippyMap`, `IsoView`, `MULTI_PALETTE`/multi-file compare, route colouring, the wellness card, every `rm`-prefixed element id, and the Esri ArcGIS tile endpoints — so this app no longer fetches map tiles at all. The FIT decoder and activity model stayed, because Video + Fit Sync still needs them. Git history up to `c9aec37` has the lot if any of it is wanted back.

## Shot Finder
`analyzeMotion()` (canvas diff) + `analyzeAudio()` (Web Audio) run in parallel, optional ML via `loadScript`/`getMlModels`/`analyzeML`. `buildSegments()` fuses signals → review via `renderTimeline`/`renderShotList` → `joinShots()` cuts/exports, all client-side.

**Signal scaling is the whole ballgame for detection quality**, and getting it wrong is subtle: the original `normalize()` divided each signal by its own global maximum over the entire video, so a single outlier (a camera re-aim, a shout, a car passing) set the scale for everything else and squashed every real shot below the fixed `0.18` threshold — a 4-minute match reliably yielded *one* detection. `normalizeRobust()` replaces it, referencing the 95th percentile of non-zero values instead, floored at 12× the noise level (the median non-zero value). The floor must be noise-relative, **not** max-relative — flooring at a fraction of the max reintroduces the same bug in weaker form, since one outlier drags the reference back up. It only binds when real events are under ~5% of the video, as above that the percentile is the larger term. `removeLocalBaseline()` subtracts a rolling median first (10s half-window for motion, 2s for audio) so slow drift — re-aiming, exposure changes, a neighbouring court's chatter — doesn't count as activity. Audio's baseline is *centred*, replacing a trailing-only average whose elevated floor for 1.5s after any hit masked exactly the follow-up shots in a quick exchange. Verified against a generated 4-minute 320x180 VP8 fixture with 40 known shot times, driven through the real page in Chromium: 1 shot before, ~40 after (±3 run to run, since 4x playback presents a slightly different frame subset each time). Synthetic-signal sweeps also cover the negative cases — pure noise and noise-plus-outliers must yield ~0, not a list of false positives.

Audio is sampled in 25ms windows (a racket impact is a ~10-30ms transient that 100ms windows smeared away) and scored on `hf`, the RMS of the signal's first-order difference — a cheap high-pass that separates a strings/ball click from wind, voices and court rumble. Motion samples divide each frame diff by the media-time gap since the previous sample, because `requestVideoFrameCallback` at `playbackRate = 4` only sees a varying subset of decoded frames and an undivided diff scales with that gap; `fillEmptyBins()` forward-fills bins no frame landed in, which otherwise read as zero motion and fragmented one rally into sub-minimum-length pieces the length filter then dropped. A silent video (no audio track, or an undecodable audio codec) is a supported case, not an error — it falls back to motion only. Note `decodeAudioData`'s callback form *also* returns a promise that rejects on failure, so it needs a no-op `.catch()` or a silent video raises an unhandled rejection despite the failure being handled.

**The expensive scan is cached** (`cached = {file, motion, audio, ml, mlInterval}`). `buildSegments()` is pure over those samples and runs in ~150-250ms on a 4-minute video, so the motion/sound/min-length/padding/ML-weight sliders re-cut via `resegmentFromCache()` with no re-scan (a scan is ~60s for 4 minutes, and before this every slider nudge paid it again). Only two things invalidate: a new file, and the ML *sample interval* or ML toggle — those change what gets measured, not how it's thresholded, so they can't be served from the cache and say so instead. `#previewVideo` is **moved** (never duplicated — one element, one decode) into `#resultsVideoSlot` at the top of the results card once results exist, and moved back to `#uploadCard` on a new file; the slot is `position:sticky` so the player stays on screen while scrolling a long shot list, since pressing play on a shot whose video has scrolled away is useless. `#uploadStatus` surfaces upload-step failures that used to fail silently (an empty `fileInput.files` after the native picker closes — seen on iOS Safari, likely a slow/failed iCloud download of the original video before Safari can hand it to the page — and `previewVideo.onerror` for an unplayable file); `fileInput.value` is reset after each `change` so re-picking the same file still fires the event. All three file inputs in this app (`#fileInput`, `#syncVideoInput`, `#syncFitInput`) use a `.visually-hidden-file` CSS class rather than `display:none`, since some mobile browsers are unreliable about firing `change` on a file input that's `display:none` at the moment the native picker hands the file back. Upload/preview/`analyzeMotion()`'s canvas sampling rely entirely on the *browser's own* video decode (no code-side codec handling possible there) — iPhone's default "High Efficiency" HEVC/H.265 recordings play fine on Safari (native hardware decode) but are a gamble elsewhere. "Frame-accurate cuts" is a plain user-toggled checkbox (decode+re-encode to H.264 via `VideoSampleSink`/`VideoSampleSource` vs. the fast keyframe-snapped `EncodedPacketSink`/`EncodedVideoPacketSource` default, see below) — it no longer carries any HEVC-specific caveat in its label since export itself doesn't care what the source codec is (fast mode never decodes at all; precise mode decodes via the platform's own WebCodecs `VideoDecoder`, same as `<video>` playback).

`joinShots()` (~`index.html:1032` onward) is the export engine: WebCodecs (`VideoDecoder`/`VideoEncoder`, native, no cross-origin-isolation requirement) plus vendored **Mediabunny** (`mediabunny.min.js`, MPL-2.0, `window.Mediabunny`) for MP4 demux/mux, since WebCodecs itself has no container support. Replaced ffmpeg.wasm entirely (see git history for that era's SharedArrayBuffer/MEMFS-cleanup workarounds, all now moot) after it broke repeatedly on GitHub Pages and hit a "bad memory" WASM-heap ceiling on longer videos — this engine streams packet-by-packet instead, so there's no fixed heap to exhaust. `wholeGopEndBoundary()` rounds a shot's end out to the next keyframe (mirroring `getKeyPacket()` rounding the start back to one) so fast mode never truncates mid-GOP — cutting mid-GOP with B-frames present can hand the muxer an out-of-order timestamp relative to that GOP's own reordering, which is exactly the kind of thing that looks fine on one test clip and breaks on the next; testing against real H.264 and HEVC fixtures (multi-shot, both modes) surfaced this and two related boundary-timestamp bugs before they shipped. Per-track `lastMaxTs` state gates only the *next* shot's starting cursor against the true previous-shot max (via the next GOP's own keyframe timestamp, not by summing packet durations, which some encodes report short/estimated on a GOP's last packet) — never individual packets within a shot, which would corrupt normal B-frame reordering. Browsers without `VideoEncoder`/`VideoDecoder` (Firefox <130, iOS <16.4) get a plain "not supported" message instead of attempting export — no ffmpeg.wasm fallback, by design.

## Video + Fit Sync
Replaced the old Shot Library, which tagged/saved clips to a browsable IndexedDB library — removed in favour of this: pick a video and a .fit activity file; there's no reliable client-side way to automatically match camera footage to GPS/motion data, so the default offset is a guess (`videoFile.lastModified − video.duration`, since a phone's file timestamp is usually close to when recording stopped) shown plainly in `#syncReadout` and adjustable via `#syncNudgeRow`'s ±0.1/1/5s buttons (`syncResetBtn` reapplies the guess). `video`'s `timeupdate` drives `onVideoTime()`, which finds the matching `.fit` index (`findIdxForTime`) and updates the HR/pace/elevation `RouteChart`s; clicking a chart calls `seekVideoToIdx()` which sets `video.currentTime` directly — the `<video>` element is the only clock here, with no separate play loop to fight it, so a chart click "during playback" just works. Charts here are indexed by **elapsed time**, not distance (`activity.t` offsets, not `activity.dist`), since a tennis match covers almost no ground and a distance axis would bunch the whole recording into a sliver of the chart.

`isWellnessFile()` only tells the user which kind of file they picked: a daily wellness export (no `record` messages, but `monitoring`/`stress_level`/`monitoring_hr_data`) can't be synced against a video, so it says so and stops. It used to be `summarizeWellness()`, which built a whole stat model for the Fit Analysis tool's wellness card; with that view gone the stats had no reader, so it is a predicate now.

**FIT internals** (shared, still used here): `parseFitFile()` is a from-scratch binary FIT decoder (no library) — reads the 14-byte header, then walks definition/data records (incl. compressed-timestamp headers) using a `BASE_TYPES` table and hardcoded field-number maps for `record`/`session` messages (global mesg nums 20/18; `lap` messages are skipped); semicircle lat/lon, scaled altitude/speed/distance per the FIT profile. `buildActivity()` derives the model: cumulative distance prefers the device's own field (falls back to `haversine()` accumulation when absent), elevation gain/loss uses a 1m-hysteresis walk over a smoothed (`movingAvg`) altitude series unless the session's `total_ascent`/`total_descent` fields are valid, moving time caps each inter-sample gap at 6s so auto-pause/stopped time doesn't inflate it.

**`RouteChart`** is a small canvas line-chart class (crosshair on hover). `_bindEvents()` fires its `onHover` callback on both `pointerdown` (a plain tap/click selects a point, not just a drag) and `pointermove` while over the canvas.

## Pose Montage
Takes a batch of photos (not video) and reorders them so similar player body positions sit next to each other, then renders the ordered sequence into an actual MP4 slideshow. Own IIFE at the very end of `index.html`, `pm`-prefixed ids/classes throughout — shares no state with the other two tools, and deliberately reuses only the *model*, not the *code*, from Shot Finder's ML path (its `loadScript`/`getMlModels`/`analyzeML` are private to Shot Finder's own IIFE).

**Pose model**: lazy-loads TF.js + `@tensorflow-models/pose-detection` (MoveNet SINGLEPOSE_LIGHTNING) from unpkg via a local `getPoseModel()` — deliberately skips coco-ssd (Shot Finder's ball detector) since there's no ball to find in a still photo, so this tool's first-use download is smaller than Shot Finder's ML toggle. Each uploaded photo is drawn onto a small working canvas (longest side capped at 480px — `MAX_DIM`, plenty for pose landmarks and much faster than running the model at full phone-camera resolution) purely for detection; the original full-resolution `Image` is what actually gets drawn into the exported video.

**Feature extraction** (`poseFeatures()`): rather than comparing raw keypoint (x,y) positions — which would treat two photos of the same swing phase as "different" just because the player is framed differently — it builds an 11-value (`FEATURE_COUNT`) vector of joint *angles* (elbow, knee, shoulder, hip, both sides), torso lean off vertical, shoulder-line tilt, and wrist-to-wrist spread relative to torso height (compact stance vs. full extension), each normalized to 0–1. This is scale- and position-invariant by construction, which is what makes "similar body position" comparable across photos shot at different distances/crops. Player *size* (bbox height of confident keypoints ÷ image height) is tracked separately, not folded into the angle vector, since it means something different (framing/zoom, not pose) — `featureDistance()` combines them as `0.75×poseDistance + 0.25×sizeDistance` so ordering primarily chains by body position but still avoids violent zoom jumps between neighbors. A keypoint below `MIN_KP_SCORE` (0.3) fills its angle(s) with a neutral 0.5 rather than a wrong number from noisy coordinates. `poseAnchors()` separately extracts hip-center/shoulder-center points (normalized to the analysis frame's own dimensions) purely for on-canvas alignment at export time — deliberately not folded into the angle vector, which is position-invariant by design and so useless for that.

Photos are filtered, not imputed: anything where MoveNet's overall confidence (`filled / FEATURE_COUNT`) comes in under 0.5 — no player found, too much of the pose occluded — or where `poseAnchors()` couldn't form both centers, gets dropped from `photos` entirely (`analyzeBtn` handler, after the per-photo loop; its object URL is revoked same as a manual thumbnail removal). A confidently-detected pose can still not belong: with ≥4 usable photos, each one's nearest-neighbour feature distance is compared against 2.5× the batch's median nearest-neighbour distance, and anything past that (a spectator, a different sport, an angle the model misread) is dropped too. `analyzeStatus` reports how many were removed and why; there's no "we guessed, here's an orange outline" path anymore — a photo either fits the sequence or isn't in it.

**Ordering** (`orderPhotos()`): builds a full pairwise distance matrix, then a greedy nearest-neighbor walk (`nearestNeighborOrder()`, start at photo 0) for an initial chain, cleaned up by a bounded open-path 2-opt (`twoOpt()`, capped at 25 sweeps) that reverses segments whenever doing so shortens the total path — the greedy walk alone tends to paint itself into a corner late on (its last few picks are whatever's left, however far), and 2-opt is what turns that into something that reads as one continuous, fluid arc rather than mostly-good-with-one-bad-jump. `< 3` photos skips straight to identity order, since neither the matrix nor 2-opt does anything useful below that. The user can still nudge the machine-picked order via the `‹`/`›` buttons on each `pmOrderedGrid` thumbnail (`data-action`/`data-pos`, delegated click handler) — plain buttons rather than drag-and-drop, since HTML5 drag-and-drop has no native touch backend and this app is phone-first.

**Export** (`buildMontage()`) is a second, simpler use of the same WebCodecs+Mediabunny engine Shot Finder's `joinShots()` uses for clip export, but going the other direction: instead of remuxing existing encoded video packets, it *encodes new video from scratch* by repeatedly drawing to a canvas and calling Mediabunny's `CanvasSource.add(timestamp, duration)`, which snapshots whatever's currently on that canvas. Canvas size is fixed per export at the average aspect ratio across the ordered photos, rounded up to even dimensions since H.264 requires that — just a reasonable default frame size, since photos are no longer contain-fit into it (see below). Per photo: `fadeFrames` of crossfade (alpha-blended against the previous photo, skipped for photo 0) followed by `holdFrames` of that photo alone, both driven off the user's seconds-per-photo/crossfade-seconds sliders at a fixed 24fps. No audio track. Same "needs WebCodecs" browser gate as Shot Finder's export (`typeof VideoEncoder === 'undefined'`).

**Alignment** (`drawAligned()`, inside `buildMontage()`): every photo is drawn via a similarity transform (rotate + uniform scale + translate) built from its `poseAnchors()` hip→shoulder vector, mapping it onto one fixed on-canvas hip/shoulder position (`targetHip`/`targetShoulder`, ~62%/32% down the frame) shared by every photo in the sequence — not chained photo-to-photo, since a fixed common target means each pose lands exactly where the last one did without small per-step errors drifting over a long sequence. This replaced the old contain-fit/letterbox draw entirely: matching body position now takes priority over keeping the whole frame in view, so a photo shot at a different distance/angle/orientation than its neighbours will commonly have parts fall outside the canvas or leave a background gap (papered over by the per-frame `fillRect`) — the explicit tradeoff for a sequence that reads as one continuous motion rather than a slideshow of separately-framed shots. This is also *why* photos without both anchor points are filtered out during analysis rather than kept with a guessed position: there'd be nothing to align them to.
