# apps/rally-clipper

Branded "Tennis Analysis" in the UI. See root `CLAUDE.md` for repo-wide conventions.

Tennis analysis: auto rally/shot detector + clip exporter, video↔.fit sync, .fit route/wellness analysis (formerly the standalone Route Mapper app, merged in), and a pose-similarity photo montage builder. Four tools under `.tool-tab-btn`/`.tool-panel` (`panel-finder`/`panel-sync`/`panel-fit`/`panel-montage`). FIT parsing/activity-model/formatting/`RouteChart` are shared top-level code (not in any tool's own IIFE, since they're pure/stateless) sitting between Shot Finder's IIFE and the other two; each tool is otherwise its own IIFE, independent of the others — Pose Montage's IIFE sits last, after Fit Analysis's. Element IDs from the former standalone Route Mapper app are all `rm`-prefixed (`rmDropzone`, `rmMapCanvas`, etc.) and its CSS uses `.rm-*`-prefixed classes on a `--rm-*` custom-property palette that aliases onto this app's own court/clay/ball theme, both specifically to avoid colliding with Shot Finder's pre-existing `dropzone`/`fileInput`/etc. Pose Montage's own ids/classes are `pm`-prefixed for the same reason.

## Shot Finder
`analyzeMotion()` (canvas diff) + `analyzeAudio()` (Web Audio) run in parallel, optional ML via `loadScript`/`getMlModels`/`analyzeML`. `buildSegments()` fuses signals → review via `renderTimeline`/`renderShotList` → `joinShots()` cuts/exports, all client-side. `#uploadStatus` surfaces upload-step failures that used to fail silently (an empty `fileInput.files` after the native picker closes — seen on iOS Safari, likely a slow/failed iCloud download of the original video before Safari can hand it to the page — and `previewVideo.onerror` for an unplayable file); `fileInput.value` is reset after each `change` so re-picking the same file still fires the event. All four file inputs in this app (`#fileInput`, `#syncVideoInput`, `#syncFitInput`, `#rmFileInput`) use a `.visually-hidden-file` CSS class rather than `display:none`, since some mobile browsers are unreliable about firing `change` on a file input that's `display:none` at the moment the native picker hands the file back. Upload/preview/`analyzeMotion()`'s canvas sampling rely entirely on the *browser's own* video decode (no code-side codec handling possible there) — iPhone's default "High Efficiency" HEVC/H.265 recordings play fine on Safari (native hardware decode) but are a gamble elsewhere. "Frame-accurate cuts" is a plain user-toggled checkbox (decode+re-encode to H.264 via `VideoSampleSink`/`VideoSampleSource` vs. the fast keyframe-snapped `EncodedPacketSink`/`EncodedVideoPacketSource` default, see below) — it no longer carries any HEVC-specific caveat in its label since export itself doesn't care what the source codec is (fast mode never decodes at all; precise mode decodes via the platform's own WebCodecs `VideoDecoder`, same as `<video>` playback).

`joinShots()` (~`index.html:1032` onward) is the export engine: WebCodecs (`VideoDecoder`/`VideoEncoder`, native, no cross-origin-isolation requirement) plus vendored **Mediabunny** (`mediabunny.min.js`, MPL-2.0, `window.Mediabunny`) for MP4 demux/mux, since WebCodecs itself has no container support. Replaced ffmpeg.wasm entirely (see git history for that era's SharedArrayBuffer/MEMFS-cleanup workarounds, all now moot) after it broke repeatedly on GitHub Pages and hit a "bad memory" WASM-heap ceiling on longer videos — this engine streams packet-by-packet instead, so there's no fixed heap to exhaust. `wholeGopEndBoundary()` rounds a shot's end out to the next keyframe (mirroring `getKeyPacket()` rounding the start back to one) so fast mode never truncates mid-GOP — cutting mid-GOP with B-frames present can hand the muxer an out-of-order timestamp relative to that GOP's own reordering, which is exactly the kind of thing that looks fine on one test clip and breaks on the next; testing against real H.264 and HEVC fixtures (multi-shot, both modes) surfaced this and two related boundary-timestamp bugs before they shipped. Per-track `lastMaxTs` state gates only the *next* shot's starting cursor against the true previous-shot max (via the next GOP's own keyframe timestamp, not by summing packet durations, which some encodes report short/estimated on a GOP's last packet) — never individual packets within a shot, which would corrupt normal B-frame reordering. Browsers without `VideoEncoder`/`VideoDecoder` (Firefox <130, iOS <16.4) get a plain "not supported" message instead of attempting export — no ffmpeg.wasm fallback, by design.

## Video + Fit Sync
Replaced the old Shot Library, which tagged/saved clips to a browsable IndexedDB library — removed in favour of this: pick a video and a .fit activity file; there's no reliable client-side way to automatically match camera footage to GPS/motion data, so the default offset is a guess (`videoFile.lastModified − video.duration`, since a phone's file timestamp is usually close to when recording stopped) shown plainly in `#syncReadout` and adjustable via `#syncNudgeRow`'s ±0.1/1/5s buttons (`syncResetBtn` reapplies the guess). `video`'s `timeupdate` drives `onVideoTime()`, which finds the matching `.fit` index (`findIdxForTime`) and updates the HR/pace/elevation `RouteChart`s; clicking a chart calls `seekVideoToIdx()` which sets `video.currentTime` directly — since the `<video>` element is the only clock here (no separate play loop to fight it, unlike Fit Analysis's ride-along), a chart click "during playback" just works. Charts here are indexed by **elapsed time**, not distance (`activity.t` offsets, not `activity.dist`) — unlike Fit Analysis's route-context charts, since a tennis match covers almost no ground and a distance axis would bunch the whole recording into a sliver of the chart. Loading a daily wellness file here (no `record` messages) shows a message pointing at the Fit Analysis tab instead of trying to sync against it.

## Fit Analysis
Ported from the standalone Route Mapper app (internals below) as another tool rather than a separate app, plus a wellness-file branch — a loaded `.fit` file with no `record` messages but `monitoring`/`stress_level`/`monitoring_hr_data` (Garmin's daily background-health export, not a recorded activity) renders into a separate `#rmWellnessCard` area instead of the multi-activity map/compare view, via `summarizeWellness()`. That deliberately surfaces only resting HR (`monitoring_hr_data` fields 0/1 — usually just one or two readings a day, shown as stat cards, not a chart) and a stress-score-over-the-day chart (`stress_level` field 0, ~one sample/minute, negative sentinel values filtered out as "resting"/unmeasurable rather than charted as low scores) — Garmin's other daily-summary fields (steps, floors, detailed calories) aren't reliably documented outside their own SDK, so rather than guess at undocumented scale factors, this stays to the two series decoded with real confidence.

**Fit Analysis internals**, ported as-is from the old app: `parseFitFile()` is a from-scratch binary FIT decoder (no library) — reads the 14-byte header, then walks definition/data records (incl. compressed-timestamp headers) using a `BASE_TYPES` table and hardcoded field-number maps for `record`/`session` messages (global mesg nums 20/18; `lap` messages are skipped — no lap/split feature, removed after it turned out to be an easy mis-tap and not worth the space); semicircle lat/lon, scaled altitude/speed/distance per the FIT profile. `buildActivity()` derives the model: cumulative distance prefers the device's own field (falls back to `haversine()` accumulation when absent), elevation gain/loss uses a 1m-hysteresis walk over a smoothed (`movingAvg`) altitude series unless the session's `total_ascent`/`total_descent` fields are valid, moving time caps each inter-sample gap at 6s so auto-pause/stopped time doesn't inflate it. Map zoom range is `MIN_Z=2`/`MAX_Z=21` (`zoomAt()` clamps to it) — the Dark (World Dark Gray Base) style is a generalized basemap with a lower native max LOD than Satellite (World Imagery), so it may fall back to the placeholder tile rect at the very top zoom levels rather than showing real imagery.

**Multi-file**: the file input takes `multiple`; each loaded file becomes one entry in `activities` (`{id, fileName, data, color, visible}`, colours cycling through `MULTI_PALETTE`). `focusedId` picks the one entry driving stats/charts/readout/ride-along — `getFocused()` everywhere. The map draws every *visible* entry via `buildMapLayers()`; the focused one is always the yellow tracker (full opacity, thicker, endpoint dots), any other visible ones render thinner/dimmer in their own palette colour for comparison. The file-list card is collapsed by default behind a summary toggle (`fileListExpanded`, `#rmFileListToggle`) — expanding it shows only `FILES_PER_PAGE` (10) rows at a time via `filePage`/`#rmFilePrevBtn`/`#rmFileNextBtn`, since the list has no cap on how many files can be loaded. `renderFileList()`/`#rmFileRows` uses one delegated click handler keyed off `data-action` — `toggle`/`focus`/`remove`; `showAllBtn`/`hideAllBtn` are bulk toggles unaffected by pagination (they act on all `activities`, not just the current page).

**`SlippyMap`** is a hand-rolled pan/zoom/fit-bounds raster tile map (Web Mercator math, no Leaflet) that takes `setLayers()` (plural) instead of one route, and `setStyle()` to switch basemaps via `MAP_STYLES` — both entries are keyless Esri ArcGIS Online endpoints (tile scheme `{z}/{y}/{x}`, row before column): `dark` (World Dark Gray Base, the grey/black minimal look) and `satellite` (World Imagery, a detailed Google-Earth-style aerial view) — CARTO Dark Matter was tried first for `dark` but its basemaps now expect an API key, hence Esri; OSM "standard" and OpenTopoMap "topo" were tried too and dropped for simplicity. The "user" marker (`_drawRider`) is a small glowing circle, not an arrow — no heading needed for it — paired with a `shadowBlur`-glowed re-stroke of the focused layer's last ~14 points leading into it, so it reads as "a glowing part of the line" rather than a separate icon. Tapping a route line on the map (not a drag — `_bindEvents` tracks total pointer movement and only fires `onSelect` below a threshold) hit-tests every visible layer via `_hitTestLayers()`/`pointToSegmentDist()` and focuses whichever line was tapped, same as tapping its file-list row.

**Route colouring** (`routeMetric`: flat/speed/hr/ele, `#rmRouteColorTabs`) recolours *only the focused layer* as per-segment gradients via `computeMetricColors()` + `heatColor()` (blue→green→yellow→red, normalized to that activity's own min/max) — applying a shared gradient across multiple overlaid activities at once would conflate different scales, so other visible layers stay flat-coloured regardless of this mode. `updateRouteColorAvailability()` disables HR/Elevation when the focused activity lacks that field and silently falls back to `flat`.

**`IsoView`** (`#rmIsoCanvas`, `#rmViewTabs` toggles it against the map) is a from-scratch isometric camera: lat/lon flattened to local metres around the activity's first fix, elevation exaggerated 4x (`ZEXAG`) for a readable silhouette, projected via a 2:1 dimetric transform (`_iso(p,camX,camY,camZ)`) at a fixed default angle (`this.rotation = -Math.PI/4`) that the user orbits manually by dragging the canvas (`_bindEvents()`: pointerdown/pointermove/pointerup/pointercancel, `this.rotation += dx*0.012`) — it does not auto-rotate to face the direction of travel; the rider marker is a small glowing circle (matching the map's) with its own trailing glowed line segment, not an arrow. A dragged pointer that never cleanly releases (finger lifted off-screen, or the view switched away mid-gesture) would otherwise leave `setPointerCapture` retargeting clicks on *other* controls (like the Map tab) to this canvas forever — `_bindEvents()` guards against that with an `_endDrag()` released on `pointerup`/`pointercancel` on both the canvas and `window`, on `window`'s `blur`, and explicitly from `applyViewMode()` whenever the view switches away from ride-along. Camera *position* (not rotation) is eased toward the current scrub target — possibly fractional, interpolated mid-segment during playback via `_pointAt(idx)` — by a running `requestAnimationFrame` loop (`start()`/`stop()`, ticked by `_tick(now)`, lerping `camPos`) using time-constant-based easing (`1-Math.exp(-dt/220)`) rather than a fixed per-tick fraction — this keeps the smoothing consistent regardless of actual frame rate. `setIndex()` only draws immediately when that loop isn't running (i.e. the ride-along tab isn't the active view). The ground grid sits at the rider's current elevation (`z:camZ`) so it reads as a stable local plane that slides underneath rather than one that jumps with every hill. `applyViewMode()` starts/stops the loop as the ride-along tab is shown/hidden; `setActivity()` also stops it and reseeds `camPos` from scratch (rotation persists across activities/scrubbing since it's user-set, not derived from the route). Shares the same `onChartHover(idx, targetT)` index as the map marker and chart crosshairs, so scrubbing a chart or hitting Play animates this view too. Play (`#rmPlayBtn`) is a `requestAnimationFrame` loop that tracks real wall-clock time against the focused activity's own recorded timestamps (`a.t`) via a binary-search lower bound (`findIdxForTime(t, targetT)`) — 1x is realtime, `#rmSpeedTabs` (1x/4x/16x/32x, `playSpeed`) scales how fast simulated activity-time accumulates per real ms rather than stepping a fixed index/tick. The elapsed-ms counter (`playElapsedMs`/`playLastFrameTime`) is module-level, not local to the play-button closure, specifically so a manual seek (see below) can rebase it and playback resumes from there instead of the next frame snapping back.

**`RouteChart`** is a small canvas line-chart class (crosshair on hover). `_bindEvents()` fires its `onHover` callback on both `pointerdown` (a plain tap/click selects a point, not just a drag) and `pointermove` while over the canvas. Every chart's `onHover` is wired to `seekToIdx()`, not `onChartHover` directly — `seekToIdx()`/`seekToActivityMs()` update the shared `playElapsedMs` before calling `onChartHover`, so clicking or dragging a chart *while Play is running* rebases where playback continues from instead of being overwritten by the next animation frame (previously a click mid-playback had no visible effect, since the play loop's own per-frame `onChartHover` call immediately snapped the position back). One shared hover index (`onChartHover`) drives the map marker, ride-along position, all chart crosshairs, and the readout bar together, always reading from the *focused* activity. Pace vs. speed display (`PACE_SPORTS`) and the km/mi `unit` toggle are global and re-render the whole view. `applyViewMode()` must set the map/iso wrap's `.show` class *before* either canvas's `resize()` runs — resizing while `display:none` measures a 0×0 box and permanently zeroes that canvas until the next full re-render. `showError()` messages (one per skipped file) auto-remove themselves after 6s. Selecting a different route (map tap, file-list row, visibility toggle) no longer re-fits the map's pan/zoom — only loading a brand-new file does (`renderMap(fit)`'s `fit` param, `isNewMap` check).

## Pose Montage
Takes a batch of photos (not video) and reorders them so similar player body positions sit next to each other, then renders the ordered sequence into an actual MP4 slideshow. Own IIFE at the very end of `index.html`, `pm`-prefixed ids/classes throughout — shares no state with the other three tools, and deliberately reuses only the *model*, not the *code*, from Shot Finder's ML path (its `loadScript`/`getMlModels`/`analyzeML` are private to Shot Finder's own IIFE).

**Pose model**: lazy-loads TF.js + `@tensorflow-models/pose-detection` (MoveNet SINGLEPOSE_LIGHTNING) from unpkg via a local `getPoseModel()` — deliberately skips coco-ssd (Shot Finder's ball detector) since there's no ball to find in a still photo, so this tool's first-use download is smaller than Shot Finder's ML toggle. Each uploaded photo is drawn onto a small working canvas (longest side capped at 480px — `MAX_DIM`, plenty for pose landmarks and much faster than running the model at full phone-camera resolution) purely for detection; the original full-resolution `Image` is what actually gets drawn into the exported video.

**Feature extraction** (`poseFeatures()`): rather than comparing raw keypoint (x,y) positions — which would treat two photos of the same swing phase as "different" just because the player is framed differently — it builds an 11-value (`FEATURE_COUNT`) vector of joint *angles* (elbow, knee, shoulder, hip, both sides), torso lean off vertical, shoulder-line tilt, and wrist-to-wrist spread relative to torso height (compact stance vs. full extension), each normalized to 0–1. This is scale- and position-invariant by construction, which is what makes "similar body position" comparable across photos shot at different distances/crops. Player *size* (bbox height of confident keypoints ÷ image height) is tracked separately, not folded into the angle vector, since it means something different (framing/zoom, not pose) — `featureDistance()` combines them as `0.75×poseDistance + 0.25×sizeDistance` so ordering primarily chains by body position but still avoids violent zoom jumps between neighbors. A keypoint below `MIN_KP_SCORE` (0.3) fills its angle(s) with a neutral 0.5 rather than a wrong number from noisy coordinates. Photos where MoveNet's overall confidence (`filled / FEATURE_COUNT`) comes in under 0.5 — no player found, or too much of the pose occluded — get their feature vector replaced with the dataset's mean vector (`analyzeBtn` handler, after the per-photo loop) so they still slot into the chain somewhere unobtrusive instead of skewing distances toward zero; they're flagged `lowConfidence` and outlined (`.pm-low-confidence`) in the ordered grid as a "we guessed" signal.

**Ordering** (`orderPhotos()`): builds a full pairwise distance matrix, then a greedy nearest-neighbor walk (`nearestNeighborOrder()`, start at photo 0) for an initial chain, cleaned up by a bounded open-path 2-opt (`twoOpt()`, capped at 25 sweeps) that reverses segments whenever doing so shortens the total path — the greedy walk alone tends to paint itself into a corner late on (its last few picks are whatever's left, however far), and 2-opt is what turns that into something that reads as one continuous, fluid arc rather than mostly-good-with-one-bad-jump. `< 3` photos skips straight to identity order, since neither the matrix nor 2-opt does anything useful below that. The user can still nudge the machine-picked order via the `‹`/`›` buttons on each `pmOrderedGrid` thumbnail (`data-action`/`data-pos`, delegated click handler) — plain buttons rather than drag-and-drop, since HTML5 drag-and-drop has no native touch backend and this app is phone-first.

**Export** (`buildMontage()`) is a second, simpler use of the same WebCodecs+Mediabunny engine Shot Finder's `joinShots()` uses for clip export, but going the other direction: instead of remuxing existing encoded video packets, it *encodes new video from scratch* by repeatedly drawing to a canvas and calling Mediabunny's `CanvasSource.add(timestamp, duration)`, which snapshots whatever's currently on that canvas. Canvas size is fixed per export at the average aspect ratio across the ordered photos (each photo is then contain-fit/letterboxed into it, so mixed portrait/landscape bursts don't get cropped), rounded up to even dimensions since H.264 requires that. Per photo: `fadeFrames` of crossfade (alpha-blended against the previous photo, skipped for photo 0) followed by `holdFrames` of that photo alone, both driven off the user's seconds-per-photo/crossfade-seconds sliders at a fixed 24fps — this crossfading is what "fluid overall" actually means in the output, since the ordering step only controls *sequence*, not how photos transition into each other. No audio track. Same "needs WebCodecs" browser gate as Shot Finder's export (`typeof VideoEncoder === 'undefined'`).
