# apps/531-bbb

5/3/1 lift tracker. See root `CLAUDE.md` for repo-wide conventions (file structure, git, verify-before-commit).

`route` var + `render()`/`go()` swap views (Setup/Home/Train/History/Progress). State (`settings`/`state`/`history`) in `localStorage` via `load()`/`save()`. Plate math: `plateBreakdown`, `diffPlateCounts`, `buildSessionPlateStages`. `history.json` is a static export, unused at runtime except that `checkRemoteHistory()` fetches and merges it in on boot.

Cycles never auto-advance: `advanceDay()` stops at week 3 (wraps `dayIndex` but leaves `week` there) — the only way into cycle N+1 is the "Start new cycle" button at the bottom of Home (`doStartNewCycle` → `pendingStartCycleConfirm` modal → `doConfirmStartNewCycle`, which still fires the existing `queueCycleUp()` TM-bump modal). Home's Cycle Progress grid (`renderCycleProgress()`) pages independently via `viewingCycle` (`‹›` = `cycleNav`, clamped to `[1, state.cycle]`, reset to `state.cycle` whenever `go('531home')` runs) and shows a ⚙ (`openCycleTMEdit` → `pendingCycleTMEdit` modal, current cycle only) for editing `settings.tms` without leaving Home — the Home "Training maxes" card was removed (Setup still has the full editor). Grid cells (`doCycleCellClick`) look up `viewingCycle`, not `state.cycle`: a done cell opens `editingHistoryIdx` (edit-history modal) same as before; an empty cell just sets `state.week`/`dayIndex` and re-renders Home — it no longer auto-navigates into Train, so "Start workout" is a separate deliberate step. "Choose a different day" (`doPickDay`) opens `pendingPickDay` (a `{dayIndex,week}` modal with per-lift icon rows and week buttons — `pdSelectLift`/`pdSelectWeek`/`confirmPickDay`) instead of `prompt()`.

Train adds a fixed `WARMUP_SCHEME` (40/50/60% ramp) ahead of the main sets, computed alongside them in `computeWorkout()`; warm-up weights are fixed (not editable) but every set — warm-up, main, and BBB — has a completion control: warm-up/main use a round `.done-tick` button (grey outline → green fill+border when done; `doToggleSetDone`, `warmupDone`/`mainDone` arrays), with the AMRAP reps `<input>` sitting in the same `.set-right` row beside the tick; BBB still uses the 5 `.bbb-dot` counters (`bbbDone`). Ticking one auto-starts a rest clock (`startRest(REST_WARMUP|REST_MAIN|REST_BBB)`) shown as a fixed bottom banner that counts UP from 0:00 (elapsed "since last set", `restStartAt`) rather than down to a target — it never auto-hides, staying on screen (and still counting) until the next set restarts it or Skip dismisses it; `REST_WARMUP|REST_MAIN|REST_BBB` are kept only as `restTarget`, a per-set-type threshold that flips the banner's colour (green → `.overtime` red) and fires one vibrate once elapsed passes it, as a "you've gone long" nudge rather than a cutoff. The clock itself is one global `setInterval(updateRestTimerUI, 250)` that patches `#restTimerLabel` and the `.overtime` class directly rather than going through `render()` every tick (which would thrash the page); `restLabelText()` is reused both there and by `renderTrain()` so a fresh render shows the real elapsed time immediately instead of a placeholder. Train's back arrow (`topbar(..., confirmDiscard=true)` → `data-action="backDiscardConfirm"`) opens `pendingDiscardConfirm` (holds the target route) rather than navigating straight away, since nothing is persisted until Finish; confirming calls `go(pendingDiscardConfirm)`. Train's set/BBB weights are editable (`sessionWeights`, lazily seeded by `ensureSessionWeights()` from the computed prescription, reset on every `go()`) — editing a `.weight-input`/`#bbbWeightInput` updates `sessionWeights` and re-renders so `buildSessionPlateStages` recomputes live off the edited values (one continuous stage sequence spanning warm-up → main → BBB); `doFinishWorkout()` logs `sessionWeights`, not the raw computed ones (warm-up completion isn't persisted to history, it's session-only). Train's lift-head card has a `History` toggle (`liftHistoryOpen`, reset to collapsed by `go()` on every route change so it never carries over into the next session) that reveals `renderLiftHistoryPanel(lift)` — a read-only, capped-at-`LIFT_HISTORY_LIMIT`(6) list of that lift's past sessions (week label, date, top-set performance/est. 1RM), with a "+N earlier" note pointing at the full History tab; deliberately no Edit/Delete there (unlike `renderHistoryItem`), since it's a quick glance mid-workout, not the history editor.

History opens on its Progress subtab by default (`historyTab = 'progress'`), Log one tap away; each Progress chart card is itself clickable (`data-action="viewLiftLog"`) as a shortcut into the Log subtab pre-filtered to that lift (sets `historyTab='log'` + `historyLiftFilter`), with a `View log ›` hint in the card's corner. History's Log tab is filterable/groupable by lift (`historyLiftFilter`, chip row from `liftFilterChips()`) — "All" groups entries under per-lift `.history-group` headers via `renderHistoryItem()`, a specific lift shows a flat list. Each AMRAP main-set row shows a `.pr-target` line (`prTargetLine()`) below its "Target: N+ reps" line: `bestE1rmForLift()` takes the max of `e1rmSeries()` (the same series Progress charts) and `repsNeededForPr()` solves the Epley formula for the smallest whole rep count at the set's *current* (possibly hand-edited) weight that would beat it, so it recomputes live as `sessionWeights` changes; with no prior AMRAP logged for that lift it shows a "sets your baseline" message instead. The Progress subtab's e1RM charts have their own `progressCycle` cycle nav (`progressCycleNav()`, same `.cp-toolbar`/`.cp-navbtn` markup as Home's cycle grid), `0` meaning "all cycles combined" (the original behaviour) and `1..state.cycle` scoping `e1rmSeries(lift, cycle)` to one cycle's logged sets — unlike `viewingCycle` it isn't reset on navigation, since it's just a display filter, not workout-selection state. `historyKey()` (used by `mergeHistoryArrays()` to dedupe on `checkRemoteHistory()`/import) deliberately excludes `cycle` from its identity key — a workout is the same workout regardless of which cycle number it's tagged with, so correcting a past entry's cycle (e.g. backfilling legacy `cycle:0` rows once the real cycle is known) and re-merging updates it in place instead of duplicating it.
