# apps/531-bbb

5/3/1 lift tracker. See root `CLAUDE.md` for repo-wide conventions (file structure, git, verify-before-commit).

`route` var + `render()`/`go()` swap views (Setup/Home/Train/History/Progress). State (`settings`/`state`/`history`) in `localStorage` via `load()`/`save()`. Plate math: `plateBreakdown`, `diffPlateCounts`, `buildSessionPlateStages`. `history.json` is a static export, unused at runtime except that `checkRemoteHistory()` fetches and merges it in on boot.

Cycles never auto-advance: `advanceDay()` stops at week 3 (wraps `dayIndex` but leaves `week` there) — the only way into cycle N+1 is the "Start new cycle" button at the bottom of Home (`doStartNewCycle` → `pendingStartCycleConfirm` modal → `doConfirmStartNewCycle`, which still fires the existing `queueCycleUp()` TM-bump modal). Home's Cycle Progress grid (`renderCycleProgress()`) pages independently via `viewingCycle` (`‹›` = `cycleNav`, clamped to `[1, state.cycle]`, reset to `state.cycle` whenever `go('531home')` runs) and shows a ⚙ (`openCycleTMEdit` → `pendingCycleTMEdit` modal, current cycle only) for editing `settings.tms` without leaving Home — the Home "Training maxes" card was removed (Setup still has the full editor). Grid cells (`doCycleCellClick`) look up `viewingCycle`, not `state.cycle`: a done cell opens `editingHistoryIdx` (edit-history modal) same as before; an empty cell just sets `state.week`/`dayIndex` and re-renders Home — it no longer auto-navigates into Train, so "Start workout" is a separate deliberate step. "Choose a different day" (`doPickDay`) opens `pendingPickDay` (a `{dayIndex,week}` modal with per-lift icon rows and week buttons — `pdSelectLift`/`pdSelectWeek`/`confirmPickDay`) instead of `prompt()`.

Train is a **one-set-at-a-time** screen (`focusIdx`, session-only, reset by `go()`). `sessionSets(w, sw)` flattens the workout into one ordered array of 11 sets (3 warm-up + 3 main + 5 BBB), each `{kind, idx, weight, repsLabel, pct, amrap, label, short, done, editable}`; completion still lives in `warmupDone`/`mainDone`/`bbbDone` and `sessionSets` only reads them. The screen renders a progress rail (`.sess-rail`, one tick per set, breaks between phases), a `.focus-card` for `sets[focusIdx]`, and a `.sess-list` of every set (tap a row → `focusSet` → sets `focusIdx`). `doMarkFocus()` translates the single Done button into whichever completion store backs the focused set (BBB is a count, so marking set `i` done means `bbbDone = i+1`) and then `advanceFocus()` jumps to the first set still outstanding. `doBumpWeight(dir)` steps the focused set's weight by `settings.increment`, clamped at `barWeight()`; warm-up sets are `editable:false` so their steppers are `visibility:hidden` (dimming them read as a broken button). The focused weight also has a direct `#focusWeight` input, bound in `bindEvents()`, which writes to `sessionWeights.main[idx]` or `.bbb` depending on the focused kind.

`renderBarVisual(weight, stage)` draws the bar as it should actually be loaded, with IWF plate colours (`PLATE_COLOUR_KG`/`_LB`) and heights proportional to denomination; plates in `stage.add` get an outline, so the plates you physically have to move are the ones highlighted. **It reads `stage.total`, not `plateBreakdown(weight)`** — `buildSessionPlateStages` deliberately keeps big plates loaded and trims small ones, so the canonical minimal breakdown would draw a bar that contradicts the "+ 1×2.5" line printed under it. On Home the same function is called with `stage = null`, which falls back to `plateBreakdown()` — correct there, since there is no session in progress to be consistent with.

Known wart, pre-existing and untouched: on the way *up* `buildSessionPlateStages` greedily fills the *delta* from the largest denomination down rather than reconsidering the whole load, so a session accumulates small plates (a 50kg top set can end up as 4×2.5 + 4×1.25 a side instead of 1×15). It was invisible while plate maths was a text line; drawing the bar makes it obvious.

Every set still auto-starts a rest clock on completion (`startRest(REST_WARMUP|REST_MAIN|REST_BBB)`), shown as a fixed bottom banner counting UP from 0:00 (elapsed "since last set", `restStartAt`) rather than down to a target; it never auto-hides, staying on screen until the next set restarts it or Skip dismisses it. `REST_*` are kept only as `restTarget`, a per-set-type threshold that flips the banner's colour (green → `.overtime` red) and fires one vibrate once elapsed passes it. The clock is one global `setInterval(updateRestTimerUI, 250)` patching `#restTimerLabel` directly rather than going through `render()` every tick; `restLabelText()` is reused by `renderTrain()` so a fresh render shows real elapsed time immediately.

`repsInput` is now actually written to: an `input` listener on `input.reps` stores the typed AMRAP count per set index. It was previously declared and reset but never populated, so typing reps and then ticking any set (which calls `render()`) silently wiped them; `doFinishWorkout()` reads the live input when present and falls back to `repsInput[i]`, which matters because the field only exists in the DOM while its set is focused.

Train's back arrow (`topbar(..., confirmDiscard=true)` → `data-action="backDiscardConfirm"`) opens `pendingDiscardConfirm` (holds the target route) rather than navigating straight away, since nothing is persisted until Finish. Train's weights are editable (`sessionWeights`, lazily seeded by `ensureSessionWeights()`, reset on every `go()`); `doFinishWorkout()` logs `sessionWeights`, not the raw computed ones (warm-up completion isn't persisted, it's session-only). The lift-history panel (`liftHistoryOpen`, reset by `go()`) now sits below the session list rather than in a lift-head card — a read-only, capped-at-`LIFT_HISTORY_LIMIT`(6) list, deliberately with no Edit/Delete since it is a mid-workout glance, not the history editor.

History opens on its Progress subtab by default (`historyTab = 'progress'`), Log one tap away; each Progress chart card is itself clickable (`data-action="viewLiftLog"`) as a shortcut into the Log subtab pre-filtered to that lift (sets `historyTab='log'` + `historyLiftFilter`), with a `View log ›` hint in the card's corner. History's Log tab is filterable/groupable by lift (`historyLiftFilter`, chip row from `liftFilterChips()`) — "All" groups entries under per-lift `.history-group` headers via `renderHistoryItem()`, a specific lift shows a flat list. Each AMRAP main-set row shows a `.pr-target` line (`prTargetLine()`) below its "Target: N+ reps" line: `bestE1rmForLift()` takes the max of `e1rmSeries()` (the same series Progress charts) and `repsNeededForPr()` solves the Epley formula for the smallest whole rep count at the set's *current* (possibly hand-edited) weight that would beat it, so it recomputes live as `sessionWeights` changes; with no prior AMRAP logged for that lift it shows a "sets your baseline" message instead. The Progress subtab's e1RM charts have their own `progressCycle` cycle nav (`progressCycleNav()`, same `.cp-toolbar`/`.cp-navbtn` markup as Home's cycle grid), `0` meaning "all cycles combined" (the original behaviour) and `1..state.cycle` scoping `e1rmSeries(lift, cycle)` to one cycle's logged sets — unlike `viewingCycle` it isn't reset on navigation, since it's just a display filter, not workout-selection state. `historyKey()` (used by `mergeHistoryArrays()` to dedupe on `checkRemoteHistory()`/import) deliberately excludes `cycle` from its identity key — a workout is the same workout regardless of which cycle number it's tagged with, so correcting a past entry's cycle (e.g. backfilling legacy `cycle:0` rows once the real cycle is known) and re-merging updates it in place instead of duplicating it.
